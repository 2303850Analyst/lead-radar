> relevance до Details; полноразмерная quality-выборка и production reliability

## 1. Контекст и результат для пользователя

Пользователь вводит произвольное описание физического бизнеса: «барбершоп»,
«место, где стригут мужчин», «фулфилмент для маркетплейсов» или другую нишу.
LeadRadar до запроса карт показывает, как понял задачу. Однозначный intent
запускается автоматически. При неоднозначности пользователь выбирает одну из
трёх трактовок. Ошибка «категория Geoapify не настроена» больше не является
обычным UX для понятной бизнес-категории.

Готовым считается не наличие вызова Kimi, а измеримый результат:

- intent правильно сопоставляется с canonical taxonomy;
- ни одна придуманная категория не уходит в Geoapify;
- сомнительный запрос не запускает ложный поиск;
- найденная карточка имеет решение о релевантности и evidence;
- offline и live evaluation проходят зафиксированные пороги;
- пользователь получает terminal state за установленное время.

## 3. Scope v0.4.0

### Входит

1. Версионированная canonical taxonomy минимум из 30 бизнес-категорий.
2. Provider catalog и deterministic compiler для Geoapify.
3. Exact/synonym/fuzzy resolver без внешнего API.
4. Server-only Kimi adapter и strict Structured Output.
5. `POST /api/search/plan`.
6. Confirmation UX перед расходом Geoapify quota.
7. Интеграция SearchPlan в текущий JSON/NDJSON search.
8. Deterministic relevance для всех лидов; Kimi для спорных top-20 только после
   отдельного data-flow gate и по независимому выключенному по умолчанию флагу.
9. Golden datasets, offline eval, fault injection и manual live eval.
10. SLI, usage и cost report без raw inputs/responses.

### Не входит

- автоматическая генерация новых provider categories моделью;
- второй картографический provider;
- web search Kimi;
- поиск или генерация телефонов, email, сайтов и соцсетей через AI;
- CRM, массовый outreach, auth/multi-tenancy и постоянная БД;
- обещание полного реестра рынка;
- автоматическое выполнение неоднозначного intent;
- внешний contractual SLA до production tier и статистически достаточных данных.

Runtime validation выбирается один раз: JSON Schema является source of truth,
а `ajv` является validator implementation. Validator обязан отклонять unknown
fields и out-of-allowlist IDs; schema compilation выполняется при загрузке
module, а не на каждом запросе.

Provider boundary после refactor:

```ts
type GeoapifyExecutionPlan = {
  provider: "geoapify";
  providerCatalogVersion: string;
  categoryIds: GeoapifyCategoryId[];
  center: [longitude: number, latitude: number];
  countryCode: "RU" | "BY" | "KZ";
  radiusMeters: number;
  language: "ru" | "be" | "kk";
  limit: number;
};

type CompiledCandidateFilter = {
  version: string;
  excludedNormalizedTerms: string[];
  fields: ["name", "address", "providerCategoryIds"];
};
```

Если payload имеет только `location`, search service сначала вызывает
`provider.geocode({location, countryCode, language}, signal)`, затем создаёт
final execution plan. Runtime order: `intent_resolution -> geocoding (optional)
-> provider_compilation -> places`.

Provider API становится двухфазным: `searchPlaces(executionPlan, signal)` и
`fetchDetails(placeIds, signal)`. Между ними search service применяет
`CompiledCandidateFilter`, radius/country validation и dedupe. Exclusions
компилируются из `excludeQueries` в нормализованные literal terms без raw regex
или provider syntax; исключённая карточка не должна расходовать Details quota.

Provider methods получают эти типы и AbortSignal, но не `description`,
`primaryQuery`, related text или client-supplied selectors.
`SearchPlan.executionPreview` является derived read-only preview; compiler заново
строит execution plan из validated canonical IDs и server catalog.

```dotenv
MOONSHOT_API_KEY=

KIMI_PLANNER_REASONING_EFFORT=low
KIMI_CLASSIFIER_MODEL=kimi-k2.6
KIMI_REQUEST_TIMEOUT_MS=30000
KIMI_CLASSIFIER_MAX_ITEMS=20
KIMI_LEAD_CLASSIFICATION_ENABLED=false
KIMI_MAX_CONCURRENCY=1
KIMI_MIN_START_INTERVAL_MS=20000
KIMI_ADMISSION_TIMEOUT_MS=20000
KIMI_CIRCUIT_FAILURE_THRESHOLD=3

```

Правила:

- default `QUERY_INTELLIGENCE_MODE=deterministic`;
- `kimi` разрешён только при server-side key;
- runtime жёстко ограничивает Tier 0 одной активной и одной ожидающей задачей;
- client bundle и health response не содержат key;
- base URL allowlisted; произвольный URL из request запрещён;
- точные model IDs проверяются через `/v1/models` и canary call.
- значения выше являются безопасным local Tier-0 profile; production profile
  после подтверждения минимум Tier-1 использует timeout `12000`, deadline
  `45000` и собственный bounded retry максимум `1`;
- автоматические retries SDK всегда выключены; scheduler и retry принадлежат
  приложению;
- `SEARCH_PLAN_SIGNING_SECRET` генерируется отдельно от API-ключа и не попадает в
  client, logs или Git.

## 7. API contract

### `POST /api/search/plan`

Вход сохраняет текущий `SearchPayload` и добавляет optional:

```json
{
  "locale": "ru-RU",
  "countryCodes": ["RU"]
}
```

Ответ: `SearchPlan` из архитектурного документа.

В `v0.4.0` `countryCodes` содержит ровно одну страну. Support matrix:

| Страна | Допустимые locale | Статус |
|---|---|---|
| `RU` | `ru-RU` | supported |
| `BY` | `ru-BY`, `be-BY` | pilot, обязательный golden/live gate |
| `KZ` | `ru-KZ`, `kk-KZ` | pilot, обязательный golden/live gate |

Другая страна или несколько стран возвращают контролируемый `unsupported`, а не
молча используют Россию. Называть это покрытием всего CIS запрещено до
расширения матрицы и evaluation.

HTTP semantics:

- `200 ready`;
- `200 needs_confirmation`;
- `200 unsupported`;
- `200 degraded` при безопасном fallback;
- `400` только для синтаксически невалидного payload;
- `429` только для внешнего request/auth/product limiter до принятия job, не для
  internal Kimi scheduler и не как raw upstream error;
- `5xx` не используется для ожидаемого semantic outcome.

### `POST /api/search`

- старый payload продолжает работать;
- для подтверждения клиент передаёт `confirmedConceptIds` вместе с
  `confirmationToken`;
- token stateless и имеет формат
  `base64url(canonical claims).base64url(HMAC-SHA256(secret, claimsPart))`;
- claims содержат token version, `requestCacheKey`, `sourcePlanHash`, allowed
  alternatives, taxonomy/catalog/policy versions, `iat` и `exp` (TTL 10 минут);
- сервер проверяет подпись, expiry, версии и что выбранные IDs действительно
  были предложены в конкретном плане, а cache key совпадает с повторно
  нормализованным raw intent;
- после подтверждения создаётся новый plan с `method=user_confirmed`,
  `parentPlanHash=sourcePlanHash` и новым `planHash`; server-side plan storage для
  проверки token не требуется;
- client не передаёт provider selectors;
- ambiguous/unsupported plan не вызывает Geoapify;
- successful ready response сохраняет старые top-level fields и получает
  optional `plan`;
- lead получает optional `relevance`.

JSON response union:

```ts
type SearchEndpointResponse =
  | SearchResponse
  | {
      error: string;
      code:
        | "SEARCH_PLAN_CONFIRMATION_REQUIRED"
        | "SEARCH_PLAN_UNSUPPORTED"
        | "SEARCH_ADMISSION_LIMIT";
      plan?: SearchPlan;
    };
```

`ready` и executable `degraded` возвращают обычный `SearchResponse`; у degraded
plan уже есть allowlisted deterministic concept, а недоступна только optional AI
capability. Если безопасного concept нет, status обязан стать
`needs_confirmation`/`unsupported`. `needs_confirmation` возвращает HTTP 409, `unsupported` —
HTTP 422, admission rejection — HTTP 429 с `Retry-After`. Semantic outcome не
маскируется фиктивным пустым `SearchResponse`.

`SEARCH_ADMISSION_LIMIT` относится только к внешнему limiter. Если уже принятый
job не получил внутренний Kimi slot, он возвращает deterministic fallback либо
`needs_confirmation` с reason code `KIMI_ADMISSION_TIMEOUT`, но не HTTP 429.

### NDJSON

Добавляются stages `intent_resolution`, `provider_compilation` и
`relevance_classification`; optional `geocoding` идёт до runtime compilation.
Поток заканчивается ровно одним `result` или
`error`; для semantic error запись содержит те же `code` и optional `plan`.
Client cancellation aborts Kimi и provider requests. Клиент обязан игнорировать
неизвестные additive stages.

## 8. Resolver algorithm

1. Validate length, list count, locale и country.
2. Unicode NFKC, lowercase по locale, `ё -> е`, collapse spaces.
3. Exact alias lookup.
4. Ranking: exact alias `1.0`; иначе
   `0.6 * token Jaccard + 0.4 * character trigram Dice`. Negative alias блокирует
   candidate. Shortlist: top-20 со score >= 0.35.
5. Если один deterministic кандидат проходит policy, вернуть `ready` без Kimi.
6. Если shortlist неоднозначен, Kimi получает top-20 candidates.
7. Если shortlist пуст или слаб, Kimi получает весь компактный allowlisted
   каталог (до 60 concepts); это обязательный zero-token-overlap path.
8. Если каталог превысил 60 concepts, выпуск блокируется до появления
   проверяемого semantic/embedding retrieval; произвольное усечение запрещено.
9. Если Kimi выключен или недоступен, вернуть deterministic result либо
   `needs_confirmation`/`unsupported`, не запускать provider наугад.
10. Validate finish reason, JSON Schema, enum IDs и negative aliases.
11. Decision policy выбирает `ready`, `needs_confirmation`, `unsupported` или
    executable `degraded`. Последний допустим только при уже известном
    allowlisted deterministic concept и недоступной optional AI capability;
    иначе требуется confirmation/unsupported.
12. Provider compiler строит selectors только после `ready`/validated confirmation.

Deterministic auto-run: score >= 0.92, gap до второго >= 0.15, negative conflict
отсутствует. Порог входит в `decisionPolicyVersion`.

`requestCacheKey`: normalized intent + входные versions; `planHash`:
`requestCacheKey` + status + validated resolution + exact model ID + execution
preview + все versions. Объекты сериализуются с рекурсивной сортировкой keys,
списки intent нормализуются/дедуплицируются/сортируются, SHA-256 от UTF-8 bytes
записывается lowercase hex. `confirmationToken` в `planHash` не входит.

Kimi transport использует SSE `stream: true`, накапливает только
`delta.content`, проверяет terminal finish reason и `[DONE]`, затем выполняет
AJV validation. Оборванный stream или `finish_reason=length` отклоняется целиком.
Schema artifact задаёт все enums, length/item bounds, `uniqueItems` и
`additionalProperties:false` на каждом nested object. `npm run schema:check`
обязан пройти AJV и официальный MFJS validator `walle` перед release.

## 9. Kimi model gate

Перед выбором production primary одинаковый hidden benchmark запускается для:

- `kimi-k3` с `reasoning_effort=low`;
- `kimi-k2.6` с thinking disabled и простой schema;
- `kimi-k2.7-code` как schema-focused candidate.

Чтобы не превращать выбор модели в сотни дорогих повторов, offline suite из 500
intent выполняется детерминированно и с mock transport. Live shortlist:

- 100 hidden intent на каждую модель, один прогон;
- после выбора победителя 30 самых сложных intent x 3 повтора для stability;
- classifier benchmark — максимум 100 разрешённых candidate records на модель
  batch-вызовами и только после data-flow gate.

Модель исключается независимо от среднего score, если найдено хотя бы одно:

- out-of-catalog ID;
- provider URL/category вне allowlist;
- prompt injection success;
- invented organization/contact;
- schema acceptance без локальной валидации;
- unsafe auto-run ambiguous intent.

Среди оставшихся выбирается Pareto-победитель: auto-run precision, macro-F1,
stability, p95 latency, actual cost. Exact model ID фиксируется в evaluation
report и release notes. Плавающие aliases запрещены.

`kimi-k3` является первичным кандидатом planner, но не объявляется выбранной
production-моделью до live evaluation по пользовательскому аккаунту. У K3
лимит `<=300` относится к финальному JSON content; reasoning usage учитывается
отдельно, его completion p95 gate — `<=1200` tokens. Для K2.6/K2.7 действуют те
же schema/safety gates, даже если они дешевле.

Post-search live benchmark блокируется отдельным Kimi data-flow gate:
документируются передаваемые поля, права источника на onward processing,
возможные персональные/конфиденциальные сведения, country-specific privacy и
retention, а также допустимый режим Customer Content по
[Kimi Terms](https://platform.kimi.ai/docs/agreement/modeluse) и
[Privacy Policy](https://platform.kimi.ai/docs/agreement/userprivacy). До
закрытия gate работает только deterministic relevance и флаг
`KIMI_LEAD_CLASSIFICATION_ENABLED` остаётся `false`.

## 10. Golden datasets

### Planner: минимум 500 cases

| Сегмент | Количество |
|---|---:|
| 30 категорий x 5 русских формулировок | 150 |
| CIS-языки, смешанная речь, транслит, опечатки | 120 |
| Неоднозначные запросы | 60 |
| Unsupported/non-place | 60 |
| Prompt injection/invalid | 60 |
| Hard negatives | 50 |

Split: 60% development, 20% regression, 20% hidden holdout. Перефразы одного
семейства не могут попасть в разные splits. Два разметчика, Cohen's kappa >= 0.80.
Не менее 30 cases обязаны иметь zero token overlap с canonical labels/aliases;
они проверяют full compact catalog path, а не расширение словаря задним числом.

### Classifier: минимум 600 candidates

- 400 balanced: по 100 `matched`, `maybe`, `rejected`, `not_checked`;
- 200 с реальным распределением;
- только synthetic или normalized source observations;
- никаких телефонов, email, raw responses и реальных lead lists в Git.

Реальные evaluation artifacts создаются только после проверки лицензии и
data-flow. Если хранение допустимо, candidate-level artifact находится вне Git в
зашифрованном каталоге `work/evaluations/`, имеет ограниченный доступ и TTL 30
дней; в Git остаются SHA-256, версии и агрегаты. Если хранение запрещено,
разметка выполняется над transient session и сохраняются только агрегаты — это
явно отмечается как ограничение воспроизводимости.

### Post-search contract

Внутренний `CandidateEvidence` содержит только `candidateId`, nullable `name`,
allowlisted `providerCategoryIds`, nullable `locality` без улицы/дома и nullable
`sourceDescription`. Сервер строит его из нормализованного `Lead` и
`LeadSourceObservation`; client не может подставить evidence.

`Lead.relevance.status` принимает `matched`, `maybe`, `rejected` или
`not_checked`; `source` — `deterministic`, `kimi` или `not_checked`. Каждый
result имеет reason codes и пары field/value только из реально присутствующих
полей `CandidateEvidence`. До data-flow gate Kimi не получает реальные
карточки: deterministic путь работает локально, а недостаток evidence или сбой
optional classifier возвращает `not_checked` без удаления карточки.

## 11. Quality gates

### Hard gates, нулевой допуск

1. Unknown canonical/provider IDs: `0`.
2. LLM-generated provider URL/filter/category: `0`.
3. Invented organizations, contacts или facts: `0`.
4. Prompt injection successful auto-run: `0`.
5. Accepted plans with invalid schema: `0`.
6. Claims without evidence pointers: `0`.
7. API keys/raw responses in logs, Git, fixtures или client bundle: `0`.
8. Ambiguous/unsupported intent вызывает Geoapify requests: `0`.

### Planner metrics

- Top-1 accuracy однозначных intent >= 92%;
- macro-F1 canonical concepts >= 0.90;
- precision auto-resolved subset >= 95%;
- auto-resolution coverage однозначных intent >= 80%;
- correct concept in Top-3 >= 98%;
- recall `needs_confirmation|unsupported` >= 95%;
- unsafe auto-run ambiguous intent = 0;
- label stability за 3 live runs >= 95%;

### Classifier metrics

Эти gates обязательны только если `KIMI_LEAD_CLASSIFICATION_ENABLED=true`.
При выключенном AI-classifier report помечает их `N/A: data-flow gate open`, а
deterministic classifier всё равно проходит evidence/invariant suite.

- macro-F1 >= 0.85;
- precision `matched` >= 0.90;
- precision high-confidence `matched` >= 0.95;
- recall `maybe` >= 0.85;
- recall `rejected` >= 0.90;
- recall `not_checked` >= 0.90;
- evidence coverage = 100%.

### Реальный search comparison

- 10 бизнес-категорий;
- Москва, Минск, Алматы;
- 20 кандидатов на задачу;
- два независимых разметчика;
- Precision@20 >= 85%;
- high-confidence precision >= 95%;
- уникальных релевантных кандидатов минимум на 15% больше baseline;
- падение precision против baseline не более 5 процентных пунктов;
- необъяснимые merge/split duplicates <= 5%.

В Git сохраняются только агрегированные metrics, версии и hashes.

## 12. SLO, timeout и reliability gates

Обычная p95 latency и contractual SLA Kimi официально не опубликованы. Поэтому
до измерений на нашем ключе действуют два разных профиля, а не одно обещание.

### Local pilot: вероятный Tier-0, один пользователь

| Метрика | Gate после calibration |
|---|---:|
| Первый progress event p95 | <= 0,5 с |
| Пауза между progress events для long-running job | <= 2 с в >=99% jobs |
| Deterministic plan p95 | <= 150 мс |
| Fast path без Kimi, terminal base result p95 | <= 15 с |
| Kimi inference p95 | <= 20 с; timeout 30 с |
| Kimi-assisted terminal base result p95 | <= 55 с |
| Global terminal deadline | 60 с |
| Terminal business response <=60 с | >=98% valid attempts |
| Kimi logical success | >=95% dispatched calls |
| Safe fallback after Kimi failure | 100% |
| Kimi queue overflow | <=5% AI-eligible attempts |
| Geoapify endpoint success | >=98% dispatched calls |
| Geoapify 429 rate | <=1% calls |
| Mock/load controlled response на 1000 requests, concurrency 10 | >=99,5% |
| Unhandled 5xx в fault suite | 0 |

Calibration начинается только после 100 valid searches и 50 фактических
Kimi-calls; до этого отчёт показывает raw counts, p50/p95 и не объявляет SLO
выполненным. У Tier-0 concurrency `1` и официальный предел `3 RPM` по
[Kimi rate limits](https://platform.kimi.ai/docs/pricing/limits), поэтому:

- `maxRetries=0` на SDK и в interactive Tier-0 path;
- не более одного Kimi-call на поиск;
- minimum start interval 20 с;
- очередь содержит максимум один ожидающий job и ждёт максимум 20 с;
- post-search AI classifier выключен.

Один global `AbortSignal` ограничивает все stages. Максимумы local profile:
Kimi inference 30 с, geocoding 5 с, Places 7 с, Details 15 с, normalization 1 с.
Queue timeout заканчивается `needs_confirmation` и не суммируется с новым
Kimi-call. Admission wait входит в общий 60-секундный deadline, а каждый stage
получает `min(stageBudget, remainingGlobalBudget)`, поэтому максимумы не
складываются сверх deadline. На global deadline возвращается partial result с явными
`not_checked` либо контролируемый status.

### Production target

External beta блокируется, пока не подтверждены минимум Kimi Tier-1,
коммерчески подходящий тариф Geoapify, server auth/quota и измеренная ёмкость.
Geoapify Free официально даёт 3000 credits/day, до 5 requests/s и best-effort
support; он годится для пилота, но не является основой внешнего SLA. Paid plans
публикуют default 99,5% monthly availability SLA: см.
[Geoapify pricing](https://www.geoapify.com/pricing/).
Цели после этого:

| Метрика | Production target |
|---|---:|
| Первый progress event p95 | <= 0,3 с |
| Kimi plan p95 / timeout | <= 8 с / 12 с |
| Fast path terminal base result p95 | <= 12 с |
| Kimi-assisted terminal base result p95 | <= 25 с |
| Global terminal deadline | 45 с |
| Product terminal availability, rolling 30d | >=99,5% |
| Live-provider completion | >=99,0% с одним provider |
| Kimi queue overflow | <=0,5% AI-eligible attempts |

Первые 500 live jobs за 7 дней — только пилотная калибровка. Договорный SLA не
публикуется до 10 000 репрезентативных jobs за 28 дней и нижней 95%-й
доверительной границы не ниже обещанного уровня.

SLI считаются раздельно:

- `valid attempt` прошёл schema/auth/product-limit validation;
- terminal business availability допускает `completed`, `needs_confirmation`,
  `unsupported` и безопасный degraded status;
- live-provider completion считается только среди executable accepted searches,
  исключая явный client abort, но включая upstream 429/5xx как failures;
- корректный пустой provider result является completion, но отдельно снижает
  search yield;
- быстрая controlled error выполняет terminality, но не live-provider completion;
- details completeness считается по `checked/not_checked`, а не маскируется как
  отсутствие данных.

Provider budget telemetry считает calls и оценочные credits на search. Для Free
pilot alert срабатывает на 70% дневного лимита, после 90% Details выполняется
только по явному открытию лида, после 95% новые live searches останавливаются с
понятным quota status; demo-данные не маскируются под live.

User-facing текст local pilot: «известная категория обычно до 15 секунд; новая
формулировка с AI может занять до минуты». Product target после Tier-1: «обычно
до 30 секунд; максимум 45 секунд».

## 13. Cost gates

- <= 3000 input tokens, <= 300 final JSON content tokens и <= 1200 total
  completion tokens p95 с учётом reasoning на planner;
- <= `$0.02` на AI-assisted plan;
- если post-search AI gate закрыт и feature включена: <= `$0.10` на
  классификацию 100 leads;
- не более одного интерактивного Kimi planner call;
- classifier вызывается только после data-flow gate для спорных карточек, max 20
  за batch, и не входит в synchronous Tier-0 path;
- повтор идентичного intent/versions в одном worker instance даёт LRU cache hit
  и 0 новых AI calls; cache ограничен 500 semantic resolutions и TTL 24h;
- usage из API является source of truth для отчёта.

## 14. Testing pyramid

| Layer | Объём | Что проверяет |
|---|---:|---|
| Unit/invariants | все decision branches | normalize, aliases, fuzzy, policy, hashes, compiler, validator |
| Property/fuzz | >= 10 000 inputs | Unicode, длины, injection, schema/allowlist invariants |
| Offline integration | 500 + 600 cases | полный planner/classifier pipeline с mock Kimi |
| API contract | >= 20 tests | plan/search JSON, NDJSON, compatibility, abort, errors |
| Fault injection | >= 12 tests | timeout, 429, 5xx, malformed, refusal, length, empty response |
| Browser E2E | >= 6 journeys | ready, confirmation, unsupported, degraded, cancel, restore |
| Live Kimi shortlist | 100 intents/model | `/models`, strict schema, hidden holdout, latency, usage, cost |
| Winner stability | 30 hard intents x 3 | variation and safety of exact chosen model ID |
| Live Geoapify | 30 tasks | three-city precision comparison without raw persistence |

Regression rule: ни одна ключевая metric не падает более чем на 2 процентных
пункта относительно последнего принятого evaluation report.

Load `1000/concurrency 10` выполняется с mock upstream и проверяет наш limiter,
deadline, queue и terminal states; Tier-0 Kimi не используется в этом прогоне.
Live Kimi нагрузка ограничивается фактическим rate tier аккаунта.

Количество unit tests само по себе не является gate. Каждый acceptance criterion
ссылается минимум на один test/report row; покрываются все ветви
`ready/needs_confirmation/unsupported/degraded`, empty/full catalog path,
confirmation expiry/tampering, limiter, circuit breaker, deadline и abort.

## 15. Acceptance criteria

1. «Барбершоп», «мужская парикмахерская» и «место, где стригут мужчин» дают один
   canonical concept; pet grooming входит в forbidden negative set.
2. Не менее 30 zero-token-overlap формулировок доходят до full compact catalog
   Kimi path и не получают преждевременный `unsupported`.
3. Неоднозначный «склад» не вызывает Geoapify до confirmation.
4. Confirmation принимается только с valid HMAC token конкретного плана;
   tampered, expired, stale и не предложенный concept отклоняются без provider.
5. Понятный unknown больше не отдаёт generic 422: ответ содержит status,
   reason codes и до трёх alternatives либо явный unsupported.
6. Старый payload `v0.3.1` работает без Kimi key и сохраняет прежние top-level
   response fields.
7. Location-only payload проходит geocoding до final compilation; countryCode
   сохраняется в execution plan. Скомпилированный exclusion отбрасывает карточку
   до Details, а старое exclude-поведение покрыто regression test.
8. Kimi никогда не формирует provider request.
9. Все SearchPlans проходят schema, taxonomy, provider allowlist, AJV и MFJS
   `walle` validation.
10. При timeout/429/5xx/malformed Kimi известная категория работает, неизвестная
   безопасно требует confirmation.
11. Каждый `matched` AI-result имеет минимум один допустимый evidence pointer;
    при открытом data-flow gate AI-classifier не получает реальные карточки.
12. Client cancellation прекращает текущие Kimi и Geoapify fetches.
13. RU/BY/KZ support matrix и отклонение multi-country/unsupported страны
    покрыты contract и golden tests.
14. SLO, accuracy, reliability, cost и hard gates из разделов 11-13 пройдены для
    фактического local/production profile.
15. `npm run lint`, `npm run build`, `npm test`, `npm run schema:check` и новый
    `npm run eval:offline`
    завершаются с exit code 0.
16. `npm run eval:kimi:live` и real search comparison пройдены перед tag; live
    suite не запускается в обычном CI без secret.
17. Evaluation report содержит commit SHA, app version, exact model IDs,
    prompt/taxonomy/catalog/schema/policy hashes, dataset versions и агрегированные
    metrics.
18. `changes_log.md`, `ROADMAP.md`, README/API version, `package.json` и
    annotated tag согласованы как `v0.4.0`.

## 17. Rollout и rollback

1. Merge code с default `QUERY_INTELLIGENCE_MODE=deterministic`.
2. Прогнать offline suite.
3. Подключить key только локально и выполнить `/models` + schema canary.
4. Запустить hidden benchmark трёх моделей.
5. Включить Kimi только для owner/local user.
6. Не включать post-search Kimi до закрытия data-flow gate; planner тестируется
   отдельно на пользовательском описании категории.
7. Выполнить 30 real search tasks и заполнить evaluation report.
8. Release/tag `v0.4.0` только при `GO`.

Rollback:

- переключить `QUERY_INTELLIGENCE_MODE=deterministic` без отката provider search;
- при regression вернуть предыдущую taxonomy/catalog version;
- optional plan/relevance fields позволяют откатить UI без миграции localStorage;
- отозвать Kimi key при подозрении на утечку;
- не удалять evaluation report и version hashes.

## 18. Definition of Done

Работа завершена только когда:

- код реализован по принятой архитектуре;
- все acceptance criteria имеют ссылку на тест или проверенный report row;
- hard gates имеют ноль нарушений;
- offline suite, mandatory live Kimi planner suite и live Geoapify suite пройдены;
- live classifier suite обязательна только при CLOSED data-flow gate и включённой
  post-search AI feature;
- SLO и cost gates подтверждены фактическими usage/latency и размером выборки;
- post-search Kimi либо прошёл data-flow gate и conditional gates, либо остаётся
  технически выключенным и явно помечен `N/A` в report;
- evaluation report имеет `GO`;
- release discipline проекта выполнена полностью.
